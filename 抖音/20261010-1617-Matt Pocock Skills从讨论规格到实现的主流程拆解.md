# 速览

## 一句话主旨
讲述者拆解自己怎么用 Matt Pocock Skills：这套技能不接管流程，只以可组合的小技能补上讨论、规格、拆单和实现。正常开发更推荐 grill-with-docs 把决策落成文件，再按复杂度决定是否生成规格、拆成可独立交付的工单，并用红绿循环的 TDD 和双维度代码审查完成实现。

## 核心要点
- 讲述者称这套技能在 GitHub 上约有 20 万 star，grill-me 在 skills.sh 的安装量已超过 80 万次且还在增加。它要解决四件事：结果不符合预期、废话太多、代码异常难处理、代码质量难保证。办法是补流程而不接管流程，并按单一职责写成可以组合的小技能。
- 选型上，绿地项目第一版讲述者更倾向 Superpowers，因为计划更细，定完后智能体更能自动跑，长程任务的自动化也更高。日常小改动则换回这套技能，Superpowers 太重，模型变强后过细计划也被认为偏浪费。大型或多人协作更适合 OpenSpec，规格里保留变更记录，否则讲述者认为会变成屎山交差；这套技能守的是细节质量。
- 技能分用户手动触发，和由模型在别的技能里主动调用两类，以维持单一职责。grill-me 与 grill-with-docs 都会调用 grilling，澄清流程写在 grilling 中，两个入口本身都很短。grill-with-docs 还会调用 domain-modeling，规定讨论结束后如何把决策落盘；只用 grill-me 时，讨论不会写成文档，里面主要是提问流程。讲述者建议正常开发用前者，只想把问题想清楚时再用后者。
- 主流程依次是讨论、规格、需求工单和实现。澄清后用 to-spec 生成规格，讲述者称之为 ADR，记录做什么以及为什么不做什么，免得几个月后人和智能体都不知道当初为何选型。to-tickets 再拆成带依赖、可独立交付的小工单：不是横向做完所有功能的数据库、service、控制器和 UI，而是每个功能自己走完一整条纵向切片。
- 实现步骤是用户调用的入口，实际会进入 TDD 和 code review。标准 TDD 包含红、绿和重构；讲述者说这里的 TDD 只有红绿循环，重构放到 code review，并说这是原话里的安排。红绿是指先写测试，实现还不存在所以测试失败，再写能通过的最简代码。审查由两个子智能体分别核对编码标准和规格，分开报告，避免一个维度掩盖另一个。
- 讲述者认为这些纪律以前难守住，原因是人的惰性、团队受最短板限制，以及领导压进度时会赶工。打地基的工作体感不强，现在更适合交给 AI。AI 写代码变快后，前期成本下降、收益上升，规格驱动已接近事实标准，剩下的差别主要是规格文档如何设计。直接张口描述被比作 freestyle，出得快，但质量不稳。
- 可以按复杂度跳步，但要自己权衡利弊。极小改动可以不用流程；一句话讲不清就用 grill；更复杂再出规格；多个功能点才用 to-tickets。一个 session 仍说不清，或得边做边看才知道目标时，用 wayfinder 排出带优先级和依赖的工单，再逐张选择 grill、research、prototype 或实现。research 查仓库里能发现但模型不知道的信息，脑中信息用 grill 固化，prototype 用来做更高保真原型。
- GitHub 上的 issue 和 PR 用 triage 分成缺陷、需求、人做、智能体能做、要补信息、要评估和不必做。setup 安装后配一次 tracker 和 triage 标签，不用 triage 可以不配。复杂 bug 用 diagnosing-bugs，重构优化是很耗套餐的另一入口。teach 分章生成带题目的 HTML，但要先准备上下文；讲述者更推荐只追问、不直接给答案的西格玛技能。handoff 会写 Markdown 交接文件，不同于 compact。拿不准时用 ask-matt。
