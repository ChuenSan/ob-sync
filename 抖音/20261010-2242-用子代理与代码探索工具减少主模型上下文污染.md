# 速览

## 一句话主旨
作者认为，探索阶段大量无关信息会占用模型注意力，影响后续实现质量。实操将代码探索交给子代理，配合代码探索 MCP 定位文件，只把关键结论与文件线索返回主代理，并在 AGENTS.md 中绑定技能与探索工作流，减少主上下文污染。

## 核心要点
- 作者将同一模型产出差异主要归因于填充的上下文，认为多数场景下调整模型参数的成本收益不成正比；其以注意力偏重开头与结尾、每个 token 都会占用注意力，说明上下文应少且精确。
- 据视频描述，多数任务的探索阶段比实现阶段消耗更多上下文，反复 grep、find、read 可能带入大量无用数据；作者因此让子代理负责探索，仅将有用信息汇总给主代理。
- 探索工具需按代码库和语言选择，作者为 Pi 安装代码探索 MCP，重载后检查服务是否可用；原文对工具名称的转写不清，但展示的用途是按查询条件定位相关内容，再直接读取目标文件。
- 作者比较了内置 MCP 与插件支持，暂时保留原仓库插件方案；其介绍的 Code Mode 可在沙箱中执行一段脚本，批量调用 MCP 查询并统一返回结果，而非每次工具调用都单独返回。
- 视频将虚拟模型解释为按任务难度切换模型的路由，并认为子代理也能达到类似效果；简单任务用便宜模型不一定降低总成本，跨模型切换还可能影响缓存，实际费用取决于用法。
- 安装后的工具说明尚未与 Matt Pocock Skills、子代理流程绑定，作者让模型修改 AGENTS.md，而不修改 SKILL.md，因为技能包更新可能覆盖手工改动，工作流调整应保留在自己的说明文件中。
- 当时 AGENTS.md 只有 55 行，作者暂不压缩，并建议超过 100 行再用其提到的写作技能精炼；实现阶段偏向选择速度快的模型，理由是测试反馈循环建立后，犯错可以通过快速修复纠正。
- 对局内核驱动实操中，子代理先调用探索 MCP，再读取文件并返回重点文件与结论；据视频展示，主代理上下文约为 4.8%，三个探索子代理各自已到约 10%，实现结果留待次日验收，视频未展示最终完成情况。
