# 速览

## 一句话主旨
临时项目先命名为「模型战争」，装上 Matt Pocock Skills 并切到 GM 5.3 后，用 grill-me 做顶层可行性分析，再接着做粗粒度需求。追问边界事先划清，没想清的玩法不提前定死；方向是让模型写脚本做可回放对抗，用来看编码能力，也方便自媒体持续产出。

## 核心要点
- 因为觉得 Arena 这个名字不好用，项目临时叫「模型战争」，不叫竞技场。本地建同名文件夹，初始化 Git，主分支不用 master，绑定远端但先不推送。再在 Pi 安装 Matt Pocock Skills，重新加载后做一次 setup：用 local markdown 而不是 GitHub Issue 管任务，避免和仓库原有 issue 冲突；标签默认，agent 按当前环境确认。首次提交不合规范就改掉，免得开坏头。
- 这次外部项目按生产级来做，模型换到 GM 5.3，先做可行性分析，再做需求分析。用 grill-me 而不是 grill-with-docs，因为后者包着架构决策模板，会影响模型把可行性分析写好。边界要划成顶层分析，否则会越问越细。确认后用视频所说的 red for agent 技能生成文档，但不提供写法套路，只给领域关键词；视频称做的越多，错的越多。
- idea 先故意写糊，追问后再说清，并且不称为 benchmark，以免影响判断。不需要玩家，类型倾向 RTS 式领土争夺，要有策略和多模型对抗，由 AI 写脚本再跑，简单游戏挑战不够。平台倾向 Web，是否用游戏框架渲染还没定，第一版可以不要网页，也不做实时对战，脚本写一次再跑，并且每次都能回放。
- 目的有两个：写脚本对战，用来看模型编码能力强弱；做出来后自媒体能持续出视频，不用每次实战录半天。报告维度让它全部分析。决策频率现在不该想太细，追问变细就要纠正。引擎考虑过用 Rust 拆开跑，但改得慢，也更难让 AI 写，要不要同一套语言这题选了 B。游戏不接入模型，只放脚本。
- 调研后称已经有人做过几乎一样的东西。讲述者打开网页，说那是自己以前玩过的 Steam 游戏，视频里称为 scripts，用脚本跑对局。后续可以参考，但不要全抄，策略上要改。游戏已有多年，以前多是程序员在玩，现在可以直接上大模型。摘要确认后生成可行性报告，里面找到竞品，讲述者认为可以照着参考来做。
- 当时上下文大约占 4%，需求分析可以接着做，大约再占 5% 到 6%，模型还在视频所说的促进区，不必新开窗口。上下文占满，或两项任务不相关时，再切窗口、压缩或交接。可行性分析的内容有助于写需求。需求从用户角度列功能，一开始不要太细，有些是做的时候才浮现的，定太细后面还得改。
- 游戏机制觉得重复、不符合要求，但自己说不清想要什么，这轮不谈。玩法没定、只有实践才知道的细节先不答。能确认状态只读，回放必须每次结果完全一致。防污染和另一题先不展开。给模型看的文档觉得别扭，V0 仍先按建议来，做到实践再改。
- 公平性最重要，要测模型能力；脚本不能直接改状态作弊；确定性保证回放每次相同。先做静态校验，报错后可改几次脚本，再加练习赛。接口不公开就不容易被污染，竞品可能已受污染。第一版做回放查看器即可。提交易错就换模型，规范改后后续会遵守。模型和 Agent 已选过，架构和技术选型留到下期。
