# 速览

## 一句话主旨

视频围绕 vLLM 如何提升大模型推理服务性能展开，介绍 KV Cache、PagedAttention、前缀缓存、连续批处理、分块预填充、量化和多卡并行等机制，并说明显存池、调度器与 GPU Worker 如何协同处理请求及进行性能调优。

## 核心要点

- 逐 token 生成时，模型会重复使用先前 token 的 Key、Value 计算结果；KV Cache 将其缓存以减少重复计算，但会占用大量显存，限制并发请求数量。
- PagedAttention 将 KV Cache 按固定大小的块存放在显存池中，并通过块表映射逻辑位置与物理位置，减少连续显存分配带来的浪费；视频称 vLLM 可通过 GPU memory utilization 设置显存池大小。
- 前缀缓存可按已写满块的内容计算指纹，让共享相同前缀的请求复用缓存；视频据此建议将提示词中的固定内容放在前面、变化内容放在后面，以提高命中机会。
- 连续批处理以每个 token 的生成步骤为调度单位，完成的请求释放资源，新请求可以补入；分块预填充则将长 prompt 拆成多段，便于调度器在处理期间穿插其他请求。
- 调参经验：关注 `max-model-len`、`max-num-batched-tokens` 和 `max-num-seqs` 对请求长度、分块预填充和单步并发数的影响；若启动报错提示至少需要处理一个请求并显示 estimated maximum model length，可查看末尾估算值并检查上下文长度与显存配置。
- 量化及数据类型选择会影响显存占用和精度。配图补充：`--dtype auto` 通常按模型选择可用精度；`--enforce-eager` 可关闭 CUDA Graph 以节省显存，但可能降低速度。配图中的参数默认值以 vLLM v0.31.0 为参照，实际使用应通过 `vllm serve --help` 核对当前版本。
- 部署经验：`--model` 指定实际加载的模型，`--served-model-name` 设置 API 对外展示的名称；服务对外开放时应配置 `--api-key`。若模型单卡已能放下但请求并发不足，可考虑用 `--data-parallel-size` 增加模型副本分摊请求；张量并行和流水线并行则用于拆分模型。
- 监控经验：结合 `vllm:kv_cache_usage_perc`、`vllm:num_requests_waiting`、`vllm:num_preemptions_total` 排查显存池压力；前缀缓存命中率可用 `prefix_cache_hits_total / prefix_cache_queries_total` 观察。
