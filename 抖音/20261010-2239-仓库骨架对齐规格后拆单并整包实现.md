# 速览

## 一句话主旨
技术栈大体已经确定，这期不用 wayfinder，而用 grill-with-docs 搭仓库骨架。MiniMax 3.1 Flash 先把调研事实问清并改规格，再纵向拆工单；模型若提前写代码就打断。四张工单都可由代理独立完成，所以新开窗口用 implement-spec 整包实现，全部做完再验收。

## 核心要点
- 前两期已经跑完 Matt Pocock Skills 的 wayfinder。这期改走 grill-with-docs，目标是搭起仓库骨架，模型是 MiniMax 3.1 Flash 的预览。一次对话能把上下文对齐，就用 grill-with-docs；目标比较远，或人和模型都说不清问题时，才用 wayfinder。骨架和技术栈这边大体能确定，所以直接走前者，提示也写得比较简单。
- 模型先派任务去调研这些选型能不能用。技术栈比较多，所以跑得慢，但选型是讲述者定的，他认为问题不大。工具循环被要求尽量在 5 秒内结束，这不是硬限制，超过 5 秒但仍然快就可以，并把这个结论写进仓库，不必再加别的机制。调研得到新的事实后，原有文档里对不上的地方要改。
- 确认过的事实可以不看。格式化按推荐：以前 AI 写的 Prettier 可以不要，但格式化和测试工具必须统一，否则来回格式化会改乱提交，AI 也一样。Q4 选 B，并补至少一条能跑通的测试。两个工具有版本兼容问题，锁版本按推荐。Q6 不选推荐的 C 而选 B，命令要全部写出，方便以后手工调。
- Q7 建议是 B。讲述者本想用还在 alpha 的现成方案，避免重复造轮子；个人项目好改，自建更贵。Q8 要把白名单反转放进自建校验脚本，于是 Q7、Q8 都改为自己实现。Q9 和 QuickJS 测试都按推荐。依赖复杂度看源码，测试豁免，运行时不进库。团队项目建议锁稳定版；个人项目可追较新的 pnpm 稳定版，但要核对其他工具版本有没有被改。
- 验证当时跑在主代理里。讲述者认为最好派子代理去跑，主上下文只留结论；这轮风险点他认为没问题，所以没中途打断。他本来只想要一个 hello world，测试也只想要一条很浅的断言。随后模型直接开始改代码，这被认为不对：应先落下决策，再由人走 to-spec 和 to-tickets，不要让当前窗口做实现。
- 提前开工被打断。有些改动是讲述者自己把探索模型换成最近的免费模型。测试一次写全可能超出上下文，一个任务最好在 200K 内完成。对话要用 Contents 里的领域关键词。分不清是模型还是提示词的问题。这轮只生成规格、先不验证，多余说明可以不看。
- 规格之后用 to-tickets 纵向拆，每张都应能单独验收。这次过细，连已做过的工具链选型也进了工单，于是重来。半成品建议清掉，保持 git 工作区干净，做完一张再提交；脏工作区容易出错。现在重做代价很小，不如回到犯错前重来。重来后有 4 张工单，状态都是 Ready for，不需要人参与。
- 实现要新开窗口。每张做完都想人工看，用 implement；全部做完再验收，用 implement-spec。这里把规格交给后者，模型仍是 MiniMax 3.1 Flash。它先检查，再切分支，由子代理实现和审查，不在主代理里写。探索先派 2 个，暂用免费模型，他觉得可能和 MiniMax 3.1 有差别。第二天已经跑完，分支还没切回。check 和 quick 很快，单次检查含格式化和 lint，补跑测试也快。下一期做引擎。
